# 技术架构

## 基本原则

- **个人、轻量**：只给我一个人在一台 Mac 上用。不做账号、多人协作、云端服务、跨平台，也不搭复杂的架构。
- **够用就好**：能用简单办法解决的，不用复杂办法。每个阶段先保证真正能用，再往下做。
- **数据能长期保存、随时带走**：App 可以随时换掉，数据不会丢。

## 技术选型

| 部分 | 选择 |
|---|---|
| 桌面应用外壳 | Tauri 2 |
| 界面 | React + TypeScript + Vite，React Router，TanStack Query，Tailwind CSS |
| 界面组件 | 用 macOS 原生的下拉菜单、弹窗，加少量自己写的组件（星级、年月选择等），不用组件库 |
| 数据层 | Rust + rusqlite（自带 SQLite） |
| 包管理 | pnpm（前端），cargo（Rust） |
| 辅助脚本 | TypeScript（Node），不引入 Python 环境 |

## 分层

```
界面（React） ──┐
               ├── 调用命令 ──▶ Rust 命令层 ──▶ SQLite
AI 助手（以后）──┘              业务规则、校验、事务都在这一层
```

- 只有 Rust 端读写数据库。界面不写 SQL，只调用 `books_list`、`books_update` 这样的命令。
- 业务规则只写在命令层一处，比如「标为已读时，自动填上完成时间」。
- 以后 AI 用的 Pomelo Tools 就是这些命令的一层说明，AI 永远碰不到 SQL。

## 数据存放在哪里

| 位置 | 放什么 | 要不要备份 |
|---|---|---|
| `/Applications/Pomelo OS.app` | App 本体 | 不用，可随时重装 |
| `~/Library/Application Support/Pomelo OS/` | 个人数据根目录 | **要** |
| 　├ `pomelo.db` | 唯一的主数据库（包括设置） | 要 |
| 　├ `backups/` | 自动和手动备份 | 这里就是备份 |
| 　└ `attachments/` | 附件（v0.1 不用） | 要 |
| `~/Library/Application Support/Pomelo OS Dev/` | 开发时用的数据，和真实数据完全分开 | 不用 |
| `~/Library/Caches/` 下的缓存、本地大模型 | 可以重新下载的东西 | 不用 |
| macOS 钥匙串 | API Key 等密钥 | 不进数据目录，也不进备份 |

- 不要把数据库放进 iCloud Drive、Dropbox 这类同步文件夹，同步过程可能把数据库弄坏。想异地保存，就把**备份文件**复制过去。

## 开发版和正式版

它们不是两套软件，而是**同一份代码的两种运行方式**。唯一的区别是：用哪个数据目录。

| | 正式版 | 开发版 |
|---|---|---|
| 是什么 | 装在「应用程序」里的 `Pomelo OS.app` | 开发时直接从代码运行的窗口，改了代码马上生效 |
| 谁在用 | 我，日常使用 | AI 编程助手，用来开发和测试 |
| 数据 | `Pomelo OS/`，真实数据 | `Pomelo OS Dev/`，测试数据，随时可以清空重来 |

为什么要分开：

- **开发中的代码可能有 bug**，测试时还会反复「清空、再导入」数据，这些都不能发生在真实数据上。
- **数据库升级脚本在真实数据上执行过一次，就再也不能改了。** 开发时脚本经常要改好几遍，只能先在测试数据上试。
- **两个窗口不能共用一个数据库。** 开发版一旦把数据库升级到新版本，正式版就会因为「数据库比 App 新」而拒绝打开。

边用边开发的流程：

1. 平时用正式版。
2. AI 在开发版里做新功能。
3. 一个阶段验收通过后，运行 `pnpm app:install` 更新正式版。新版第一次打开时，会先自动备份，再升级数据库。

## 数据库升级（Migration）

- 每次改数据库结构，都新增一个编号脚本（`src-tauri/migrations/0001_xxx.sql` …），脚本编译进 App。
- App 启动时检查数据库版本：如果需要升级，**先自动备份**，再逐个执行升级脚本。
- 已经用过的升级脚本永远不改，只新增。
- 如果数据库版本比 App 还新（比如装回了旧版 App），App 会拒绝打开，防止把数据写坏。

## 备份与导入导出

| | 快照备份 | JSON 导出 |
|---|---|---|
| 是什么 | 整个数据库的完整副本 | 所有模块的数据，人能看懂 |
| 用来做什么 | 出问题时一键恢复 | 长期归档，或换到别的工具 |
| 什么时候做 | 手动；每天第一次打开 App；每次升级前 | 手动 |
| 怎么恢复 | 替换当前数据库（替换前会先备份当前的） | 导入 |

- v0.1 的导入只支持「导入到空模块」和「覆盖整个模块」，不做合并。
- Excel 原型也走 JSON 导入：先用脚本把 `柚儿园.xlsx` 转成 Pomelo 的导出格式，再用 App 导入。
- 导入文件里暂时不支持的模块会被跳过，并在确认框里说明。
- 文件里只要有一条数据不合格，就一条都不导入，并告诉你是第几条出了问题。

## 占用空间和内存

不算本地大模型和 AI 服务。「实测」是阶段 1 在这台 Mac 上量出来的，其余是估算。

| 阶段 | App 本体 | 数据库 | 附件 | 运行内存 |
|---|---|---|---|---|
| 现在（阶段 1） | 5.7 MB（实测） | 几 KB | 无 | 约 85 MB（实测） |
| v0.1（4 个模块 + Excel 数据） | 约 6～8 MB | 约 0.1 MB（实测 92 KB），之后每年增加不到 0.1 MB | 无 | 约 90～120 MB |
| v1（加上 Todo、财务、Dashboard、搜索、统计、附件） | 约 8～15 MB | 用 3 年约 5 MB，10 年约 20 MB | 0.1～2 GB，看存了多少照片 | 约 120～200 MB |
| v2（加上 AI 助手，保存对话记录） | 约 10～20 MB | 对话记录每年多 10～50 MB | 同上 | 约 150～250 MB |
| 最大估算（重度使用 10 年） | 不超过 30 MB | 不超过 0.5 GB，大部分是 AI 对话 | 可能超过 5 GB，主要是照片 | 不超过 300 MB |

- 这里的「v1」「v2」只是为了估算做的假设，以实际开发路线为准。
- 运行内存 85 MB 的构成：App 本身 29 MB，网页显示 36 MB，图形 13 MB，网络 6 MB（和「活动监视器」里看到的「内存」口径一致）。18 GB 内存的 1% 都不到；同类的 Electron 应用通常要几百 MB。
- 估算依据（实测每条记录的大小）：待办约 0.2 KB，账目约 0.15 KB，一条 300 字左右的 AI 消息约 1.3 KB。全局搜索的索引会让数据库再大 50%～100%。
- 真正占空间的是附件（比如绘画练习的照片），所以以后存照片时会先压缩。
- 备份占用约等于「数据库大小 × 保留的份数」。v0.1 保留 30 份也只有几 MB；数据库变大以后，保留规则要重新设计（阶段 6 处理）。

## AI 助手（以后再做，v0.1 不涉及）

- Pomelo 自己的 AI 助手运行在界面里，能接 OpenAI、Claude 和本地模型（Ollama），三种模型共用同一套 Pomelo Tools。
- 会修改数据的 Tool，执行前要我在界面上确认。
- 已有的 pub2md-agent（PDF / Markdown 翻译工具，Python + Django，本地运行）保持独立，不重写。以后作为「本地服务」接进 Pomelo，具体方式到 AI 阶段再定。
- pub2md-agent 已经在用 OpenAI 兼容接口。Pomelo 的模型接入也以 OpenAI 兼容接口为主（Ollama 同样支持），Claude 单独接入。
- 本地模型大概率用**千问（Qwen）**，通过 Ollama 运行。千问支持 OpenAI 兼容接口和工具调用，现有方案不用调整；云端的千问（阿里云百炼）同样是 OpenAI 兼容接口。
- 这台 Mac 有 18 GB 内存，建议用 8B 左右的量化版千问（约占 5～6 GB）；14B 左右（约 9～10 GB）也能跑，但会比较挤。
